# Orchestrator Platform — план Minimum Lovable Product

**Версія:** 1.0 · **Дата:** 2026-07-06 · **Власник:** Yaroslav
**Базується на:** аудиті CRM-orchestrator-beta-0.1 + 6 фіксах у tick.ts (вже зроблені)

---

## 1. Ціль і переозначення продукту

Стара ціль (PRODUCT.md бети): local-first пульт для одного користувача, який керує агентами над одним репо. Multi-tenant SaaS — прямо non-goal.

**Нова ціль (основна):** платформа, де користувач описує продукт однією ціллю, а система:

1. **Build** — декомпозує ціль у задачі й будує продукт групою агентів у паралелі.
2. **Deploy** — деплоїть результат в один клік з preview-посиланнями.
3. **Market** — окрема маркетинг-панель: креативи, кампанії, публікація.
4. **Measure** — аналітика продукту + аналітика витрат токенів в одному місці.
5. **Bring Your Own Model** — OpenRouter або будь-який CLI, підключення за 2 хвилини.

Наскрізний принцип: **економія токенів видима і керована** — бюджет на проєкт, live burn rate, вартість кожної задачі.

## 2. Що таке "lovable" тут (критерії, а не гасла)

MLP готовий, коли **ти сам** проходиш цей сценарій без терміналу і хочеш повторити:

> Ввів ціль ("зроби лендинг для X з формою заявки") → бачиш, як агенти розбирають її на задачі і працюють паралельно → бачиш live-стрічку "що зараз робить кожен агент" людською мовою → апрувиш merge одним кліком → тиснеш Deploy → отримуєш URL → відкриваєш вкладку Market, генеруєш 3 креативи, запускаєш кампанію → наступного дня бачиш: візити, конверсії, і що це коштувало $4.20 токенів + $15 реклами.

Кількісні ворота MLP:

- Ідея → задеплоєний продукт: **< 1 день**, **0 команд у терміналі**.
- Вартість токенів видно **до** запуску (估imate), **під час** (live) і **після** (факт), точність ≥ 95% (реальні usage-дані, не оцінка по символах).
- Підключення нової моделі через OpenRouter: **< 2 хв**, без правки коду.
- Час до розуміння "що зараз відбувається" на будь-якому екрані: **< 10 секунд**.

## 3. Фази

### Фаза 0 — Стабілізація ядра (1–2 тижні)

Без цього все інше стоїть на піску. Половина вже зроблена.

**Зроблено (у tick.ts):**

- Реальний cost-журнал (JSONL) замість заглушки; cost cap працює.
- Неблокуючий планувальник (fire-and-forget запуски, in-flight трекінг).
- Reconciliation осиротілих in-progress задач на старті (анти-deadlock).
- Відновлення існуючого PR при повторному worktree.
- Атомарний запис routing-файлу; SIGKILL-ескалація по таймауту.
- estimateCost парсить Claude Code JSON + флаг `estimated`.

**Лишилось у Фазі 0:**

- **F0.1 Точні usage-дані.** Перевести запуски на `claude -p --output-format json` і JSON-вивід Codex; журнал отримує 100% реальні токени/$, поле `estimated` зникає з нормального шляху.
- **F0.2 Postgres writer.** Схема `agent_runs` / `daily_cost` / `orchestrator_events` вже є — дописати запис подій і ранів. JSONL лишається як fallback/бекап.
- **F0.3 Worktree hygiene.** `git fetch origin main` + rebase при повторному використанні worktree; авто-видалення worktree після merge задачі.
- **F0.4 depends_on.** Рахувати залежність виконаною для статусів `done` **і** `merge-ready` (конфігуровано), інакше пайплайн штучно серіалізується.
- **F0.5 Auth на control API.** Bearer token на Hono-ендпоінти (той самий підхід, що ти вже обрав у Second Brain). Локально — токен з .env; це ж стане основою для мультиюзера.
- **F0.6 blocked-question цикл.** Зараз задача падає у `blocked-question` і вмирає. Додати: питання агента показується у стрічці → людина відповідає в UI → відповідь дописується в task body → задача повертається у backlog unflagged.

### Фаза 1 — Ядро MLP: моделі + гроші + новий UI (3–4 тижні)

**F1.1 Runner-абстракція.** Інтерфейс `Runner { run(task, ctx): RunResult }` з трьома реалізаціями:

- `ClaudeCliRunner`, `CodexCliRunner` — рефакторинг існуючого.
- `OpenRouterRunner` — API-раннер: модель = будь-який slug OpenRouter, ключ юзера, tool-use цикл з обмеженим набором інструментів (fs у worktree, bash, git). Це відкриває "підключай свої моделі".
- `CustomCliRunner` — конфіг-описаний CLI (command template, prompt через stdin/arg, парсер usage) — покриває "будь-які CLI".

**F1.2 Model Hub (UI).** Екран: список підключених моделей, ключі, ціни за 1M токенів (з OpenRouter API), призначення ролям drag-and-drop, ліміти reset. Заміна ручного `agent-routing.json`.

**F1.3 Token Control v2.** Бюджет на проєкт і на роль; попередня оцінка вартості плану до запуску ("цей запуск ≈ $2.80, підтвердити?"); live burn-метр у хедері; авто-пауза при 80/100% бюджету; журнал з фільтрами модель/роль/задача. Це — головна "lovable"-фіча для тебе.

**F1.4 UI Redesign** — окремий розділ 4 нижче. Робиться паралельно з F1.1–F1.3, бо нові фічі мають народжуватись уже в новій системі.

### Фаза 2 — Deploy (2 тижні)

- **F2.1 Deploy-адаптери.** Перший — Railway (у тебе вже є досвід і акаунт), другий — Vercel/статичний. Інтерфейс `DeployTarget { deploy(build): {url}, status(), logs() }`.
- **F2.2 Preview per PR.** Кожен PR отримує preview-URL у PR queue; кнопка "Open preview" поруч із merge.
- **F2.3 Environments.** preview / production, з тим самим two-click prod gate, який ти вже спроєктував для SB — merge у main + явний "Deploy to prod".

### Фаза 3 — Marketing tab (2–3 тижні)

Окрема вкладка верхнього рівня (не режим адмінки):

- **F3.1 Asset Studio.** Генерація рекламних текстів і креативів під продукт (агент-copywriter — сьома роль пайплайна; у тебе вже є brand-copywriter skill як прототип промпта). Варіанти A/B зберігаються у vault `07-marketing/`.
- **F3.2 Campaign Manager.** Створення кампанії: канал, бюджет, аудиторія, креативи. Перша інтеграція — Meta Ads (у тебе вже підключений MCP Meta Ads — можна переюзати цей шар). Друга — просто "export pack" (готові тексти/картинки/UTM) для ручного запуску будь-де.
- **F3.3 UTM + лінки.** Автогенерація UTM-розмітки, короткі лінки, зв'язка кампанія → продукт → аналітика.

### Фаза 4 — Analytics (2 тижні)

- **F4.1 Events ingestion.** Легкий snippet (1 script tag) → ендпоінт → Postgres. Події: pageview, click, submit, custom.
- **F4.2 Dashboard.** Візити, джерела (по UTM), конверсія форми, найпростіший funnel. Без амбіцій Amplitude — 4 графіки, які відповідають на "чи працює реклама".
- **F4.3 Unit economics view.** Головна вбивча фіча платформи: **токени + реклама + результат на одному екрані.** "Продукт коштував $6.40 токенів, кампанія $30, привела 214 візитів, 9 заявок → $4.04 за заявку." Ніхто з конкурентів цього не показує.

### Фаза 5 — Multi-tenant (після того, як сам живеш у продукті ≥ 2 тижні)

- Auth (email + OAuth), organizations, projects per org.
- **Sandboxed runners** — критично: чужі агенти не можуть виконуватись на хост-машині з `--dangerously-bypass-approvals-and-sandbox`. Ізоляція: Docker/Firecracker на задачу, ephemeral worktree всередині контейнера, egress-контроль.
- Ключі моделей per-user (шифровані), billing (спочатку BYOK-only — юзер платить за свої токени сам, ти за платформу).
- RLS у Postgres вже увімкнений на таблицях — дописати політики.

Свідомо **не** в MLP: маркетплейс шаблонів, білінг з маржею на токени, мобільний застосунок, кастомні ролі агентів, self-host дистрибуція.

## 4. UI Redesign — з "пульта авіадиспетчера" до продукту

### Діагноз поточного UI

- **Все одразу на одному екрані:** top stat bar + лівий рейл (inbox/vault) + kanban + правий рейл (live agents) + firehose drawer + модалки. Це dashboard-максималізм: 100% інформації, 0% ієрархії уваги.
- **2 380 рядків кастомного CSS** в одному файлі без системи — стилі неможливо підтримувати, вигляд "інженерний".
- **Мова інтерфейсу — внутрішня:** "firehose", "tick", "worktree", "merge-ready" — це слова розробника оркестратора, не користувача продукту.
- **Vault explorer як центральна навігація** — юзеру платформи не треба бачити файлову систему.

### Принципи нового UI

1. **Одна головна дія на екран.** Progressive disclosure: деталі — по кліку, не за замовчуванням.
2. **Розповідь замість телеметрії.** Live-стрічка пише "Developer пише форму заявки (T-031) · $0.42" замість сирих логів. Сирі логи — на один клік глибше.
3. **Гроші завжди видно, але одним числом.** Burn-метр у хедері: `$3.20 / $10 today`. Клік → повний Cost.
4. **Design tokens замість 2380 рядків CSS.** Tailwind + невеликий шар токенів у `packages/ui` (він для цього і створений). Стиль: спокійний, світлий за замовчуванням, один акцентний колір, багато повітря.

### Нова структура (5 вкладок замість режимів адмінки)

| Вкладка | Що на ній | Замінює |
|---|---|---|
| **Home** | Поле "опиши ціль" + список проєктів з прогресом і burn | Human request intake + inbox |
| **Build** | Kanban (4 колонки: Queue / Working / Review / Done) + стрічка агентів знизу; drawer задачі по кліку | kanban + live rail + firehose + vault |
| **Deploy** | Environments, preview-лінки, історія деплоїв | — (нове) |
| **Market** | Asset Studio + кампанії | — (нове) |
| **Insights** | Аналітика продукту + Cost + unit economics | cost mode + daily log |

Статуси для юзера згортаються: `backlog→Queue`, `in-progress→Working`, `review+merge-ready→Review`, `blocked-question→Working з бейджем "питання"`, `failed→Review з бейджем "помилка"`. Внутрішні 7 статусів лишаються у vault — це мапінг відображення, не зміна моделі.

### Порядок виконання UI

1. Дизайн-токени + типографіка + сітка (packages/ui).
2. Build tab (найбільша цінність — там живеш щодня).
3. Home (новий вхід у продукт).
4. Insights (на нових даних F1.3).
5. Deploy / Market — разом зі своїми фазами.

## 6. Ризики та рішення, які треба прийняти

1. **OpenRouter tool-use ≠ Claude Code.** API-раннер не має вбудованих інструментів CLI — треба свій мінімальний tool-цикл (fs/bash/git). Обмежуємо перший реліз: OpenRouter-моделі для ролей architect/pm/designer/reviewer (текст-у-текст), developer/tester лишаються на CLI-раннерах, доки tool-цикл не визріє.
2. **Sandbox — гейт для мультиюзера.** Поки виконання локальне і небезпечне, платформа — тільки для тебе. Не пускати нікого до Фази 5.
3. **Meta Ads API-ревʼю.** Публікація кампаній через API вимагає app review; план Б у MLP — export pack + ручний запуск, автопублікація пізніше.
4. **Scope creep у Market.** Перша версія — 1 канал + export, не омніканальність.
5. **Vault при масштабі.** Файлова система як БД чудова до ~сотень задач; при мультиюзері vault стає per-project git-репо (ти вже прийняв це рішення у SB — переносимо).
